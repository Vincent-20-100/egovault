# 01 — Concepts

EgoVault has eight load-bearing concepts. Master these and the rest of the
system reads itself.

## The eight terms

| Term | What it is | Where it lives |
|---|---|---|
| **Source** | A raw ingested artifact (YouTube video, audio file, PDF, web page, raw text). **Immutable** after ingest. Identified by `uid` (UUID4) and a human-readable `slug`. | `sources` table |
| **Chunk** | A `~800` token slice of a source's transcript, used as the unit of RAG retrieval. One source → many chunks. Embedded for cosine search; also indexed by FTS5 for BM25. | `chunks` + `chunks_vec` + `chunks_fts` |
| **Note** | Your distilled, human-validated knowledge document. One Markdown file per note in the vault. Has a `title`, `docstring` (one-paragraph summary), `body` (full Markdown), `tags`, `note_type`. | `notes` + `notes_vec` + `notes_fts` + `vault/notes/<slug>.md` |
| **Tag** | A `kebab-case`, lowercase, ASCII-only label. French content, but **no accents**. Notes have a `min_length=1, max_length=10` tag list. | `tags` + `note_tags` |
| **Embedding** | A unit-normalized float vector (768 dims by default with `nomic-embed-text`). Cosine distance ∈ [0,2]; smaller = closer. | `chunks_vec.embedding`, `notes_vec.embedding` |
| **Run** | One end-to-end execution of a workflow (e.g., one `ingest` call). Identified by `run_id` (UUID4). Used for monitoring, cost tracking, debugging. | `workflow_runs` in `.system.db` |
| **Taxonomy** | User-configurable lists in `system.yaml`: `note_types`, `source_types`, `generation_templates`. *Not engine constraints* — the engine validates against the configured lists. | `system.yaml` `taxonomy:` |
| **Template** | A `.yaml` file defining a prompt + output schema used by the LLM to generate a note. Lives in `config/templates/generation/<name>.yaml`. The default is `standard.yaml`. | `config/templates/generation/` |

## Lifecycles

### Source

```
raw → (fetched media) → (transcribed) → (chunked) → (embedded) → rag_ready
                                                                       │
                                                                       ▼
                                                              pending_deletion → (hard delete)
                                                                       │
                                                                       └─ failed (any stage error)
```

- `raw` — row created, no content yet
- `rag_ready` — chunks + embeddings persisted, the source is searchable
- `pending_deletion` — soft-deleted (recoverable via `restore_source`)
- `failed` — workflow errored mid-way; transcript may be partially saved

A source's text is **never** modified after `rag_ready`. To change it, delete
and re-ingest.

### Note

```
draft → active
   │       │
   ├───────┴─── pending_deletion → (hard delete)
   │
   └─ (no other states; the LLM never edits an active note)
```

- `draft` — generated by the LLM, **not yet user-approved**. Not exported to Obsidian.
- `active` — user approved the draft. Visible in the vault as a Markdown file.
- Approval normalizes/validates the taxonomy fields (`note_type`, `source_type`)
  against `system.yaml`. The generation step intentionally does NOT enforce
  taxonomy — see [04-providers.md](04-providers.md) for why.

## The two-tier knowledge model

EgoVault rejects the standard RAG mental model ("retrieve top-K chunks, paste
into prompt, forget"). It runs **two tiers in parallel**:

```
                       ┌──── Tier 1: RAG on chunks ──── precise verbatim, raw transcripts
your query ──► recall()│
                       └──── Tier 2: Compiled notes ── dense, human-titled, cross-source synthesis
```

- **Tier 1** is what classical RAG does: the source transcripts split into
  chunks, embedded, semantically searched. Good for exact facts (a specific
  number, a quote).
- **Tier 2** is what the *Knowledge Compiler* thesis adds: notes are crisp,
  reusable, validated knowledge units. They embed and rank far better than
  fragmented chunks (proven on real corpus: top-1 cosine distances ~0.10–0.13
  lower at tier 2 vs tier 1, see `.meta/audits/2026-05-20-real-notegen-test-results.md`).
- `recall()` orchestrates both. By default it tries notes first, escalates to
  chunks only if notes are insufficient (see [06-search-and-recall.md](06-search-and-recall.md)).

This is *not* generic RAG — it's a deliberate move toward an **accumulating,
densifying** knowledge store. See `docs/VISION-KNOWLEDGE-COMPILER.md` for the
full thesis.

## Tiered retrieval — `recall()`

A small, **deterministic** tool that exposes the two-tier model to the rest of
the system (CLI, MCP, future API):

```
recall(query, filters?, limit?) -> RecallContext
                                    ├── synthesis  : str   (assembled block of top results)
                                    ├── sources    : list  (each with tier, uid, title, content, distance)
                                    ├── confidence : float | None  (None at tier 0 — no LLM)
                                    └── query      : str
```

**Tier 0** (shipped, current): pure deterministic — embed query, search notes,
escalate to chunks if sparse, assemble a minimal context block. No LLM.

**Tier 1** (future, brainstorm open): add an isolated LLM call that selects,
deduplicates, and synthesizes the tier-0 result. Currently open redesign
question — see SESSION-CONTEXT open question #7 and the 2026-05-19 SOTA
synthesis card.

## Three storage locations

```
egovault/        ← public git repo (this code)
egovault-user/   ← local directory, your data
├── data/        ← vault.db (SQLite) + .system.db + media/ (audio/video downloads)
└── vault/       ← private git repo (Obsidian notes as Markdown)
```

- `data/` is binary; back it up by copying `vault.db`.
- `vault/` is text; back it up via `git push` to a private remote.
- The code repo (`egovault/`) is independent — your data never lives in it.
